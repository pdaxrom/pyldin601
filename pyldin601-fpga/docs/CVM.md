# Small-C: две ROM VM и общая цепочка инструментов

Канонические исходники находятся в соседнем `hd6303-toolchain`: `scvm.c`,
`ZCODE.ASM`, `SYSTEM.H`, Small-C и UniAS. Здесь находятся интеграция
с ramloader, примеры C и испытания с настоящими BIOS/UniDOS.

`ZVM6800.ROM` и `ZVM6303.ROM` — разные образы по 8192 байта из одного
исходника. Первый исполняет только MC6800, второй использует расширения
HD6303. Байткод C, таблица библиотеки C104–C18C и CMD-программы общие.
HD6303 INIT отклоняет загрузку на MC6800 до первой расширенной инструкции.
Существующий Lilith target сохраняет INT E8; FPGA target использует EF,
не затрагивая системный BANKCOPY E8, FAT/UniDOS E9–EB и ramloader EC.

## Запуск и ресурсы

Расположить обе ROM рядом с обновлённым RAMLOAD.PGM. Из основной оболочки
UniDOS до NC выполнить `RAMLOAD /CVM`. Загрузчик на MC6800-совместимом коде
читает bit1 E6A0, выбирает нужный файл рядом с собственным PGM и использует
обычный путь проверки/закрепления ramloader. Занятый чужой EF отклоняется
без вызова его кода. Повторная команда проверяет имя, шлюз, ABI и ISA и
переиспользует установленный модуль. Нужен RAMMAN PIN/UNPIN; прежний
системный ROM с поддержкой ramloader уже достаточен. Пересборка FPGA
и замена системных ROM для этой функции не нужны.

Расход: один банк 8 КиБ и общая резидентная таблица ramloader около 1,1 КиБ
с накладными расходами UniDOS. Новых постоянных областей VM не выделяет.
Каждый вызов сохраняет E0–FF, предыдущие BREAK/critical-error векторы и
копирует два маленьких обработчика на обычный стек. Состояние возвращается
при завершении, `exit()`, BREAK, делении на ноль и неверном байткоде.
Вложенный вызов VM сохраняет контекст родителя. Счётчик ramloader запрещает
выгрузку исполняющейся VM. Резидентная таблица остаётся до Reset.

INT EF: A=0 возвращает A=1, B=0/1 для MC6800/HD6303, X=5A56.
A=1, X=байткод запускает интерпретатор; argv/argc берутся из текущего PCB.
Результат A=0 при обычном завершении, код `exit()` либо FF при ошибке/BREAK.
Вызов возвращается RTS через штатный шлюз, восстанавливая оба селектора.
Стартовый код проверяет ABI; старые CMD с вызовом E8 надо пересобрать.

## Семантика и совместимость

Целые — 16 бит. Деление знаковое с усечением к нулю; знак остатка совпадает
со знаком делимого. Правый сдвиг арифметический, количество сдвига `n & 31`;
левый сдвиг на 16–31 даёт ноль. `-32768 / -1` возвращает -32768.
Host VM задаёт эту семантику явно, без неопределённого поведения хостового C.
В ROM исправлены остаток и сравнения с переполнением. Библиотека не зависит
от внешнего INT EE; исправлены w+, fclose/fflush, число элементов fread/fwrite,
границы/EOF fgets, нулевой strclr, строковые результаты и знак strcmp.

Исправления компилятора/ассемблера необходимы для новой host VM:
печать -32768 в обоих Small-C, беззнаковая обработка локальных суффиксов
и выражений UniAS. Seed `BOOTSTRAP/SMALLC.CMD` пересобран из исправленного
исходника. Повторная полная bootstrap-сборка даёт идентичные CMD и headers.

Это прежний Small-C: строки исходника до 79 символов, C backslash escapes
в строковых литералах не обрабатываются. Ассемблерные вставки исполняются
нативно и должны соответствовать CPU. UniDOS запрещает второй абсолютный
CMD внутри работающего CMD; `system()` поддерживает внутренние команды
и PGM. Контекст VM это ограничение загрузчика UniDOS не меняет.

## Сборка и проверки

```sh
make -C /path/to/hd6303-toolchain all pyldin test
make cvm-apps CVM_TOOLCHAIN=/path/to/hd6303-toolchain UNIAS=/path/to/hd6303-toolchain/unias
make test-cvm CVM_TOOLCHAIN=/path/to/hd6303-toolchain UNIAS=/path/to/hd6303-toolchain/unias
make test-native-assembly CVM_TOOLCHAIN=/path/to/hd6303-toolchain UNIAS=/path/to/hd6303-toolchain/unias
```

Результаты находятся в `build/cvm`; `firmware/cvm/CVMHOW.TXT` описывает
запуск из HG. Пакет содержит обе VM, обновлённый RAMLOAD.PGM, нативные
UNICC/UNIAS/UNILD/UNIAR, целевой SYSTEM.H и C-примеры. Для компиляции текущий каталог
должен содержать целевой SYSTEM.H; его вариант включает FPGA target.

Испытания проверяют общий C-тест на хосте и 601/601А × обе ISA, также при
чужих RAMMAN-банках перед VM. На каждой конфигурации выполняются 1980
независимых арифметических случаев, рекурсия, строки, файловый ввод/вывод,
вложенный SWI, `system()` с PGM, занятая выгрузка, BREAK и откат ошибок.
На MC6800 контролируется отсутствие исполненных расширенных opcode.
Нативные UNICC → UNIAS → CMD дают бинарник, совпадающий с хостовой сборкой.
Проверяются SP, нулевая страница, граница резидентной памяти и выгрузка.
Тесты работают с частными образами; физическая SD не изменяется.

`test-native-assembly` отдельно собирает BIOS, BIOS_A и XONIX с `GAME_MUSIC`
хостовым UniAS и нативным UNIAS.CMD на 601/601А × MC6800/HD6303. Исходники
и include передаются без изменения содержимого; длинные имена файлов
сохраняются под именами 8.3, до которых UniDOS сокращает обращения.
После выполнения всех команд стенд сохраняет изменённый частный образ SD.
Из него извлекаются файлы и сравниваются побайтно и по SHA256. Это не
вмешивается в состояние ожидающего клавиатуру BIOS. XONIX содержит явный
SECTION для BSS: UniAS сразу выдаёт окончательный PGM без обработки на хосте.
Результаты и `comparison.json` находятся в `build/cvm/native-assembly`.

## Самокомпиляция UniCC под UniDOS

`make test-unicc-selfhost CVM_TOOLCHAIN=/path/to/hd6303-toolchain` проверяет
два поколения компилятора на 601/601А × MC6800/HD6303, с резидентным HG,
`HANDLES 16` и выбранной ROM VM в RAMMAN. Исходник `SMALL-C/SMALLC.C`
передаётся без изменений. В текущем каталоге должен быть FPGA-вариант
`SYSTEM.H`; команды выполняются отдельно из основной оболочки UniDOS:

```text
UNICC -o UC1.ASM SMALLC.C
UNIAS -o UC1.CMD UC1.ASM
UC1.CMD -o UC2.ASM SMALLC.C
UNIAS -o UC2.CMD UC2.ASM
```

Стенд требует побайтного равенства обоих ASM хостовому результату и обоих
CMD исходному `UNICC.CMD`. Затем UC2 компилирует CVMTEST и три C-модуля;
UniAS/UniLD собирают их, UniDOS запускает полученные CMD и PGM. Проверяются
вывод `CVM TEST PASS` / `C MODULE PASS`, возврат SP и нулевой страницы,
сохранность VM и отсутствие расширенных opcode в режиме MC6800.
Исходники, файлы каждого поколения, журналы и `comparison.json` находятся
в `build/cvm/selfhost`. Для выбора одного короткого запуска или параллельных
конфигураций можно вызвать `tests/run_native_selfhost.py` с `--quick` или
`--jobs 2`, передав тот же `--toolchain`.

Перед большой нативной сборкой с вложенными include и листингом выполнить
`HANDLES 16`, затем `RAMLOAD /CVM`: стандартных 10 дескрипторов недостаточно
для второго прохода XONIX с одновременно открытыми входами, листингом,
временным кодом и PGM. Шесть дополнительных записей занимают 354 байта
обычной ОЗУ. Таблицу следует расширять из основной оболочки до загрузки VM.

## OBJ, библиотеки и нативная сборка инструментов

UniAS поддерживает PUBLIC/EXTERN, MAIN, END с точкой входа, RADIX и OBJ v1.
`SECTION` без адреса выделяет относительный BSS, не записывая его в файл;
`ENDS` возвращает в код. Открытая секция закрывается при окончании исходника.
Фиксированный `SECTION $E0` сохраняет прежний смысл. `-c`, расширение OBJ
или PUBLIC/EXTERN включают объектный формат UniCROSS. Имена интерфейса
ограничены 15 символами. Выражения с EXTERN запрещены, как в UniCROSS:
для поля структуры следует экспортировать отдельную метку.

ARKANOID и XONIX выделяют BSS через `SECTION`/`ENDS`: команда
`UNIAS -o ARKANOID.PGM ARKANOID.ASM` сразу создаёт окончательный PGM.
Обычный `DS` вне секции сохраняет нулевые байты в файле. Старый исходник
Arkanoid требовал удаления 3662 таких байтов хостовым обработчиком;
добавление секции сохраняет код и перемещения без изменений.

```text
UNIAS -c -o MAIN.OBJ MAIN.ASM
UNIAS -c -o HELP.OBJ HELP.ASM
UNILD -o APP.PGM MAIN.OBJ HELP.OBJ
UNIAR r UTIL.LIB HELP.OBJ
UNILD -o APP.PGM MAIN.OBJ UTIL.LIB
APP.PGM
UNIAR t UTIL.LIB
UNIAR x UTIL.LIB HELP
UNIAR d UTIL.LIB HELP
```

UniLD и UniAR написаны на UniCC и работают нативно на обеих VM. UniLD читает
OBJ v0/v1 и оригинальный LIB, выбирает сегменты по ссылкам, объединяет код
и BSS, разрешает байтовые и словные перемещения. `/c` создаёт CMD от $0100,
`/p` выравнивает модули по страницам; допустим `/cp`. Без `-o` используется
имя модуля с MAIN/END. Старые OBJ v0 не различают отсутствие точки входа:
первая отдельная OBJ задаёт её, последующие считаются вспомогательными.
CMD-программа сама проверяет память под BSS.

UniAR использует исходный формат UniLIB 0BB0, сохраняя OBJ без изменений.
`r` создаёт/заменяет, `a` добавляет без замены, `d` удаляет, `t` перечисляет,
`x` извлекает. Имена модулей — восемь символов. Оба инструмента понимают
`@file` со списком файлов, строками комментариев `;`/`#` и пробелами.
Выход и изменения библиотеки публикуются через временный файл; ошибка
сохраняет прежний результат.

Ограничения UniLD: 32 входных файла, 256 модулей, 512 PUBLIC определений,
по 255 PUBLIC/EXTERN в OBJ, путь до 31 символа. Один OBJ и общая память
код+BSS — до 65535 байт; LIB может превышать 64 КиБ благодаря 32-битным
файловым позициям. UniAS использует ограниченный пул символов с общими
префиксами; для больших исходников FPGA target использует также свободную
область уже установленного банка VM, описанную ниже.

```sh
make test-object-tools CVM_TOOLCHAIN=/path/to/hd6303-toolchain UNIAS=/path/to/hd6303-toolchain/unias
make game-objects UNIAS=/path/to/hd6303-toolchain/unias
```

`test-object-tools` проверяет 601/601А × MC6800/HD6303: BIOS, BIOS_A,
окончательный XONIX.PGM, XONIX из одного OBJ, из XOMAIN+XOCFG и через XCFG.LIB.
Кроссовые и нативные файлы должны совпасть. Нативный UniCC компилирует
исходники UniLD/UniAR, UniAS собирает их CMD, затем оба инструмента
исполняются. Проверяются SP, сохранение E0–FF и отсутствие расширенных
инструкций в MC6800 VM. Журналы и comparison.json — в
`build/cvm/object-native`. Стенд использует reference CPU и реальные ROM
BIOS/UniDOS, а не физическую плату.

Совместимость проверяется файлами оригинального UniCROSS 3.10 и UniLIB 1.00
из исходников `native-src`, а также запуском оригинального ULINK.CMD из ROM
диска: обычные OBJ, LIB, LSB/MSB/WORD, CMD и `/p`. Исторический ULINK имеет
ошибку при абсолютных PUBLIC значениях; UniLD сохраняет полный адрес.
Для сравнений ULINK используются новые имена выходных файлов.

Оригинальный ULINK также неверно резервирует таблицу перемещений PGM для
библиотечных модулей с внутренними ссылками; это воспроизводится с LIB
оригинального UniLIB. В других случаях он может оставлять дополнительное
заполнение между таблицей и кодом. Поэтому для таких PGM сравниваются
загружаемый код, перемещения, точка входа и BSS. UniLD корректно обрабатывает
обе разновидности библиотечных модулей.

## Обычная ОЗУ при установленном HG

UniAS для FPGA занимает 39570 байт вместо 42334: 13000 байт таблицы
символов находятся в обычной ОЗУ, продолжение — в свободной области
CC10–DEFF уже установленного банка VM (4848 байт). Дополнительный банк
не выделяется. Дескриптор VW версии 1 по CC00 задаёт адрес и размер;
сборка ROM проверяет, что код интерпретатора не пересекает эту область.
Она временная и не сохраняется при вложенных VM-приложениях; UniAS
не запускает дочерние C-программы. Хост и обычный Lilith target сохраняют
16200 байт в обычной памяти, не используя записываемую область EPROM.

С прежней FPGA VM небольшие исходники доступны в основном пуле 13000
байт. Для больших исходников после замены обеих ROM необходимо из
основной оболочки выполнить `RAMLOAD /U ZCODEVM`, затем `RAMLOAD /CVM`
либо перезапустить плату. Одно копирование ROM не заменяет уже
установленный в RAMMAN модуль.

`make test-hg-object-tools` проверяет реальный резидент HG.PGM и C backend
каталога на хосте. VM и инструменты загружаются из HG:\CVM, после
HANDLES 16. Проверяются OBJ, запуск APP, создание/просмотр/извлечение/
удаление LIB, повторная сборка Arkanoid с перезаписью PGM и большие сборки
XONIX напрямую, из двух OBJ и через LIB
на 601/601А × MC6800/HD6303. Файлы на хосте совпадают с кроссовыми;
проверяется использование дополнительного пула и сохранность дескриптора.
Отчёт — `build/cvm/hg-tools/comparison.json`. Эта конфигурация учитывает
расход обычной ОЗУ резидентами HG и ramloader.

`make test-native-firmware` проверяет прямую сборку PGM и объектную
сборку панелей/редактора NC с библиотекой NCUI.LIB, файлами @NCMAIN.LNK
и @NCEDIT.LNK. Кроме NC, собираются игры, графические и музыкальные
программы, HG, дисковые утилиты, RAMLOAD и пример GFXAY. Нативные
OBJ/LIB/PGM и карты линковки побайтно сравниваются с кроссовыми на
601/601А × MC6800/HD6303. Отчёт —
`build/bss-native/native-firmware/comparison.json`.
`unild -b` собирает контейнеры NCEDIT и RAMLOAD из двух готовых PGM
так же нативно, как на хосте; BSS задаётся SECTION/ENDS в исходниках.

Для нативных VM необходима FPGA с исправленным входом IRQ/NMI: старое
ядро могло применить ещё не выполненный opcode и испортить регистры при
переходе к обработчику. Проверки только на reference CPU этого не ловили.
Исправление находится в RTL CPU, поэтому замена файлов VM в HG его
не устанавливает. Подробности и регрессии — в [CPU.md](CPU.md).

## Раздельная C-компиляция и смешанные вызовы

Подробный план, команды и ABI находятся в `hd6303-toolchain/CVMOBJ.TXT`;
копия включена в `build/cvm`. UniCC `-c` выдаёт ASM отдельного модуля,
UniAS `-c` собирает OBJ. Поддержаны внешние переменные/массивы,
объявления функций K&R, файловый `static` и общий BSS. Имена сохраняют
прежний предел Small-C — восемь значащих символов. Исправлен учёт стека
после косвенного вызова, ошибки компиляции дают ненулевой статус.

```text
UNICC -c -o MAIN.ASM MAIN.C
UNICC -c -o HELP.ASM HELP.C
UNIAS -c -o MAIN.OBJ MAIN.ASM
UNIAS -c -o HELP.OBJ HELP.ASM
UNILD -o APP.PGM CSTART.OBJ MAIN.OBJ HELP.OBJ CRT.LIB
```

`CSTART.OBJ` идёт первым, `CRT.LIB` — последней: они задают общие границы
BSS и очищают его. Единственный стартовый модуль проверяет VM, передаёт
управление `main` и возвращает его код. Остальные C-модули содержат
байткод и данные. Для каждого адресного операнда создаётся обычное OBJ
перемещение; при загрузке PGM UniDOS добавляет базовый адрес.
Старый путь одного C-файла через SYSTEM.H в CMD сохранён.

VM-вход нативной функции начинается с `DB 86`; возвращается она через
`JMP RTSC`, передавая результат в A:B. Ссылки и указатели C указывают
именно на этот VM-вход. Сам OBJ не кодирует соглашение вызова: сырой
CPU-вход должен иметь отдельное имя и явную обёртку.

Обратный путь реализован как `INT EF A=2`, X указывает на десять байтов:
адрес функции, длина аргументов в байтах, адрес слов аргументов, результат,
статус. Все пять полей — big-endian слова. Аргументы задаются в порядке
исходного C, длина чётная, 0–64 байта. `argc/argv` не создаются. Обёртка
`cvcall` из CRT.LIB предназначена для нативного `JSR`, с тем же X.
Возвращается A=0 при обычном возврате, FF при ошибке/BREAK, либо младший
байт `exit(n)`; недопустимый адрес дескриптора возвращает A=3. Результат
значим при обычном возврате. Контекст, обработчики и стек сохраняются
для каждого входа, поэтому работают вложенные C → ASM → C вызовы.
Расширение относится к FPGA EF ABI; старый старт Lilith через E8 сохранён.

Хостовая `scvm` загружает PGM с меткой CSTART, применяет перемещения
и допускает `-b 0x8000` для проверки другой базы. Произвольные машинные
вставки по-прежнему исполняются только на CPU-стенде либо плате.

`make test-c-modules` собирает и запускает приложения через настоящий
резидент HG на 601/601А × MC6800/HD6303. Проверяются совпадение ASM,
OBJ/LIB/PGM и карт, общие данные, приватные символы, указатели, рекурсия,
нативные обёртки и обратные вызовы, оригинальный ULINK. Отчёт находится
в `build/cvm/cmodules/comparison.json`. `test-cvm` дополнительно проверяет
границы API, порядок аргументов, результат, exit/BREAK и восстановление
состояния, также при расположении VM после чужих банков.

После обновления в HG заменить установленную VM через `RAMLOAD /U ZCODEVM`
и `RAMLOAD /CVM` либо перезапустить плату. Старый уже загруженный образ
не получает новый A=2 от простого копирования файла ROM.
