# Исторический аудит исходной заготовки Пълдина-601

Этот документ фиксирует дефекты исходного прототипа 2 октября 2026.
Их текущее состояние после переработки — в [REWRITE-STATUS.md](REWRITE-STATUS.md),
проверенная версия 601/601A — в [MODELS.md](MODELS.md). Ниже сохранён исходный
аудит с его результатами и границами проверки.

Дата: 2026-10-02. Итог: текущая заготовка не является работоспособным FPGA-проектом и не соответствует согласованной архитектуре загрузки/SD. Исправления адресов сами по себе этого не устраняют. Прежние заявления о готовности и проверке загрузки следует ограничить результатами отдельных моделей, перечисленными ниже.

## Объект и границы проверки

Проверены все исходные файлы заготовки, прошивки, генератор SD, сборка, существующие тесты и их фактическое покрытие. Сопоставлены два состояния: `projects/pyldin601-classic` в FPGA-репозитории и более полный рабочий каталог `/private/tmp/pyldin601-classic`. SHA-256 обоих состояний сохранены в `source-manifest.json`. Производственный RTL в ходе этого аудита не исправлялся; новые testbench только воспроизводят дефекты.

Эталон классического поведения: `pyldin601/src/core/{devices,mc6800,mc6845,i8272,floppy,keyboard,core}.c` в репозитории эмулятора. Эталон нового SPI: функции `hd6303_spi_read`, `hd6303_spi_write`, `hd6303_spi_reset` в `devices.c`. Также проверены старые FPGA-файлы `projects/p601zero-plus/{sdcardio.v,p601zero_plus.v,ROM/DEVMAP.INC}` и аппаратные схемы/сводки `docs/hardware`.

Это аудит исходников и доступных симуляций. Синтез, place-and-route, STA, аппаратный запуск, электрические измерения и VHDL-симуляция не выполнены. GHDL, Yosys и Diamond CLI не обнаружены в PATH. Проверка Verilog со временными заглушками CPU/PLL не проверяет настоящие VHDL-модули.

## Требования пользователя и фактическое состояние

| Требование | Состояние |
|---|---|
| Классический MC6800, без HD6303 | Выбран cpu68, но изменённое ядро не проверено; фильтр допускает 6801 JSR direct |
| Плата hardware-lcd | Есть набросок top; отсутствуют законченные проект Diamond и pin/timing constraints |
| PAL TV | Есть только staging-модуль монохромного 625/50; нет функционального теста видео и запуска на плате |
| PS/2 | Основные кадры проверены; потеря непрочитанных клавиш и отсутствие клавиатурного IRQ |
| ROM/BIOS/font в RAM | Предложенное размещение в SRAM укладывается; загрузка проверена на C-модели, не в полной FPGA |
| Электронный диск в RAM | 512 КиБ предусмотрены; сохранность полного тракта при warm reset не доказана |
| SD как в новом Пълдине | Не выполнено: автономные RTL SD/FAT используются вместо программной работы CPU через SPI |
| Первичный BIOS загружает загрузчик с раздела 1 | CPU копирует LOADER, но FAT/SD выполняет аппаратный помощник |
| Загрузчик инициализирует ROM, lock, передаёт управление BIOS | Копирование и CRC есть; переход заменён дополнительной аппаратной очисткой RAM и reset |
| Кнопка reset сохраняет ROM и lock | Latch сохраняется; полный reset во время SD/SRAM операций не покрыт |
| Сначала i8272, затем LBA | Фасад i8272 частичный; совместимость со штатным BIOS не доказана |
| A/B до 12 МиБ позже | Генератор умеет такую геометрию, но классический controller/BIOS её не поддерживают; это не проверка работы в эмуляторе |

## Блокирующие ошибки и отклонения

### A01 — P0: FPGA-каталог не содержит необходимого комплекта исходников

В реальном каталоге отсутствуют `rtl/cpu6800.vhd`, `rtl/classic_pll.vhd`, `rtl/classic_video.v`. При этом top инстанцирует все три модуля. Там же отсутствуют пять расширенных RTL testbench и `prepare_images.py`; версии `classic_fdc.v` и `classic_keyboard.v` отличаются от staging. Никакой единый сохранённый набор не соответствует всем ранее названным проверкам.

Исправление: единый отслеживаемый каталог с полной зависимостью сборки, исходниками и тестами. `/private/tmp` не должен быть единственным местом хранения реализации.

### A02 — P0: верхний Verilog-модуль не разбирается компилятором

`rtl/pyldin601_classic.v:72,150,152`: конструкции `8'h60?`, `16'he628?`, `16'he632?` без разделителя распознаются как неправильные hex-литералы. Icarus возвращает syntax error. Поэтому даже `make test`, передающий `rtl/*.v`, ломается на синтаксисе top независимо от выбранного testbench.

Для продолжения аудита создана временная копия с пробелами и заглушками CPU/PLL: она elaborates. Это не исправление исходного проекта и не подтверждение полной сборки.

### A03 — P0: переименование PLL выполнено не полностью

В staging `rtl/classic_pll.vhd:14` объявляет `entity classic_pll`, но строка 20 содержит `end pll`, а configuration в конце файла — `of pll`. Это несогласованные имена design unit. Нужны исправление и анализ настоящим VHDL-компилятором/библиотекой MachXO2.

### A04 — P0: архитектура SD не соответствует запросу

`boot.asm` читает файловые порты, `fat16_file_reader.v` ищет файлы и обходит FAT, `sd_spi_block.v` сам инициализирует SD и исполняет команды. CPU выполняет лишь копирование полученных байтов. Добавленный прямой SPI не заменяет эту цепочку: его `enabled` зависит от `sd_ready`, то есть CPU получает SPI только ПОСЛЕ аппаратной инициализации карты. Через него первичный BIOS не может самостоятельно запустить SD.

Нужно перенести SD init, команды, чтение MBR/BPB, поиск LOADER и обход FAT в код MC6800, используя совместимые с новым Пълдином SPI-регистры. FAT-стример не должен участвовать в CPU boot path.

### A05 — P0: нет проверенной передачи управления классическому BIOS

`loader.asm` пишет commit и следует в FAIL. Аппаратный `classic_boot_ports` после commit удерживает CPU, очищает 0000–2FFF и подаёт reset. Это расширение схемы пользователя, а не реализованная программная передача управления. C-тест прекращает исполнение в момент `committed`; на warm reset только вызывает `MC6800Reset()` и проверяет переменные модели. Ни одной инструкции загруженного классического BIOS этот тест не выполняет после перехода.

Нужен явный контракт handoff: программная подготовка состояния, запрет дальнейших загрузочных записей, атомарное изменение overlay и получение reset vector/переход в BIOS. Последовательность должна быть проверена с исполнением самого BIOS. Аппаратный sequencer обнуления не нужен по исходному требованию и усложняет reset.

## Карта памяти, CPU и SRAM

### A06 — P1: повторное принятие одной CPU-транзакции

Top:111,133,154; `sram_byte_controller`: state 4 одновременно поднимает done и возвращает ready. На следующем фронте старое `cpu_complete=0` ещё держит request, и контроллер принимает его второй раз; top только на этом же фронте выставляет complete.

Воспроизведено `tb_duplicate_request.v`: одна операция принята дважды. Одинаковая запись RAM часто идемпотентна, но это лишняя нагрузка и неверный контракт; на reset/смене владельца риск существенно выше. Нужны отдельные latched `issued/inflight`, снятие request сразу при accept и completion только соответствующей транзакции.

### A07 — P1: классификация незавершённой транзакции не зафиксирована

`cpu_memory_request` использует текущий combinational `peripheral`, тогда как address/data/write уже защёлкнуты. После reset/переключения режима нельзя полагаться на прежний decode. Нужно защёлкнуть тип доступа вместе с адресом, привязать completion к идентификатору/владельцу и определить drain/cancel.

### A08 — P1: reset может оставить внешнюю транзакцию после сброса владельца

Кнопка сбрасывает CPU и его pending, но SRAM-контроллер сбрасывается только cold reset. Уже принятую запись он завершит. Арбитраж не имеет правила, которое исключает отнесение старого done к новому запросу. Для warm reset необходимо остановить выдачу новых запросов, закончить принятые, затем сбросить CPU-периферию; сохраняемая память/lock должны оставаться вне этого reset domain.

### A09 — P1: MC6800-совместимость CPU не доказана

Адаптация cpu68 меняет opcode fetch и CPX. `classic_opcode` разрешает 9D, тогда как классический C-core выполняет JSR direct только для HD6303. Значит утверждение «6801-only полностью отключены» неверно. Перевод всех прочих неподдержанных кодов в NOP также требует согласованного контракта; таблица допустимых ISA должна проверяться явно.

CPX high/low без переноса соответствует текущему классическому C-эталону по замыслу, но реальный HDL ALU/CC не тестировался. Требуются differential-тесты регистров, flags, RAM, stack и PC для всей классической ISA, interrupt/reset/WAI/RTI, затем boot ROM на реальном HDL CPU.

### A10 — P1: частота и такты CPU назначены без доказательства совместимости

Top создаёт CPU clock сравнением `phase>=12`; cpu68 обновляется по спаду. Нет timing constraint для generated clock, нет проверки hold относительно обоих доменов и нет сопоставления времён BIOS с фактическим числом тактов cpu68. Делитель даёт номинальный 1 МГц, что ещё не доказывает классические instruction timings. Нужны корректный clocking/enable contract и тест задержек/опросов BIOS.

### A11 — P2: отличия ROM mapping от эмулятора

ROM bank в эмуляторе выбирается `(value>>4)%5`; RTL при bank>=5 читает base RAM. Это видимое отличие для 50–F0. Нужно определить, повторяем ли аппаратную дешифрацию или выбранный эталон эмулятора; тест должен фиксировать решение.

Позитивный результат: reads BIOS F000–FFFF и ROM C000–DFFF разнесены с base RAM; CPU writes под ROM идут в base RAM, что соответствует эмулятору. Видеопамять должна всегда читать base RAM, независимо от CPU overlay.

### A12 — P1/P2: ROM guard и commit имеют два разных исполнения

Проверяется отдельный `rom_write_guard`, но top его не использует — там другая inline-защита. Проверенный guard защищает также commit-edge; top смотрит только старый locked. Текущая штатная прошивка ждёт pending перед commit, но общей гарантии для всех принятых writers нет. Сведение к одному guard после арбитра обязательно. Запрет записи должен выдавать явную ошибку/завершение, а не молча превращать write в read.

Область защиты 10000–617FF покрывает банки, BIOS и font; RAM disk отдельно и должен оставаться writable. Lock не должен сбрасываться кнопкой.

### A13 — P2: стоимость и электрический протокол SRAM ещё не проверены

Byte address -> word address/lane соответствует схеме 1M×16. Контроллер имеет setup/write/read/turnaround, но отсутствует testbench с моделью обоих byte lanes, WE/OE/CE и параметрами установленной BLL SRAM. Нет pin/I/O timing constraints и расчёта worst-case арбитража CPU/video. Частота 24 МГц сама по себе этого не заменяет.

## SPI, SD и диски

### A14 — P1: смешаны разные ABI SPI

Новый HD6303-эмулятор: +0 DATA_H, +1 DATA_L/start, +2 READY/config, +3 prescaler, +4 POUT; SD CS — бит 1 active-low; config mask 33h; reset config=23h.

Старый FPGA `p601zero-plus/ROM/DEVMAP.INC`: +0 status/config, +1 data, +2 prescaler, CS бит 0. Сам `sdcardio.v` ещё и управляет CS на отдельную byte transfer, не сохраняя его на весь SD command. Эти интерфейсы нельзя называть одним и тем же.

`boot_spi_registers` копирует порядок НОВОГО эмулятора, но reset control=02h, не 23h. Нужны сопоставление каждого read/write/reset/8bit/16bit действия и одинаковая трактовка CS/SSM/SS0/SS1/POUT. Перенос базы E6C0 -> E660 допустим: обе лежат в I/O page, E660–664 свободны в проверенной классической карте.

### A15 — P1: прямой SPI отключается после lock

Top:46,82 разрешает SPI только в boot_mode. Это не полноценный добавленный SPI-порт «как в новом Пълдине». После lock он превращается в RAM. Нужно определить постоянный доступ и арбитраж с i8272 backend; READ READY должен отражать владение, а операции должны быть атомарны от CS-low до CS-high.

### A16 — P1: два независимых SPI engine и mux вместо единого владельца

`sd_spi_block` и `boot_spi_registers` имеют отдельные shift engines. Передача ownership определяется combinational состояниями. Прямой SPI может изменить состояние карты (CMD0, block length, CRC mode), а автономный host сохраняет старые initialized/block_addressing. Получаются несогласованные знания об одной SD. Commit также не проверяет CS-high/idle raw SPI.

Нужен единый SPI byte engine и явный ownership протокол. CPU boot полностью владеет картой. Для i8272 после запуска должен быть отдельно определён backend, которому передаются проверенные SD addressing mode и partition bounds либо выполняется контролируемая повторная инициализация. Это нельзя скрывать как «тот же интерфейс».

### A17 — P1: одна ошибка SD навсегда блокирует runtime до cold reset

`sd_spi_block.fail` переводит host в FAILED; ready более не появляется. При warm reset после lock host не сбрасывается. i8272 будет возвращать ошибки бесконечно, штатная попытка BIOS reset не восстановит SD. Нужны разделение recoverable request error/init error и процедура повторной инициализации без потери ROM/RAM disk.

### A18 — P1/P2: обработка SD неполна

Есть CMD0/8/55/41/58/16, CMD17/24, CRC16 данных, bounded counters; SDHC/SDSC модели проходят. Нет чтения реальной capacity/CSD и проверки, что MBR/requests находятся в пределах физической карты. CMD0 не повторяется после единичного timeout. ACMD41 timeout задан числом попыток без проверенного времени для карт. CMD-poll ограничен 16 bytes. Нет hot removal/reinsert/error recovery. По SPI register path нет отдельного теста 8/16-bit/READY/CS.

Это ограничения прототипа, а не доказанное нарушение SD specification; при реализации нужно проверить реальные границы по спецификации и на картах, а не расширять FSM наугад.

### A19 — P1: i8272 ещё не совместимый классический controller

TC=бит 1 E6C0 записывается, но не участвует в завершении передачи. Команды завершаются сами после 512 bytes. Нет полноценного EOT/multisector/MT/early TC. Маскирование opcode[4:0] принимает комбинации, для которых остальная семантика не реализована. ST0 drive/head, busy bits, seek/sense pending и READ ID требуют сверки с BIOS и эталоном.

Односекторный фасад может быть достаточен именно для BIOS, но это нужно доказать трассой реального BIOS и форматирования, а не только собственным testbench с ожидаемыми автором ответами.

### A20 — P1: reset FDC конфликтует со state case

В `classic_fdc` обработчик select reset делает `state<=COMMAND`, затем ниже тот же always выполняет case(state) и может перезаписать state (например READ_REQ -> READ_WAIT). В READ_WAIT проверяется select bit после sd_done, но sd_error сначала выдаёт RESULT даже при held reset. Комментарий про drain не равен законченной реализации.

CPU warm reset сбрасывает FDC сразу, SD host продолжает принятый запрос; не определён drain перед новыми командой/буфером. Это особенно важно для WRITE/FORMAT.

### A21 — P1: выбор диска не защёлкнут на команду

`selected_b`, partition start/length/geometry вычисляются от живого select_reg и boot_b. Изменение выбора между приёмом команды, сбором bytes и SD-request может направить запрос в другой раздел. Команда должна фиксировать drive и geometry до окончания, включая форматирование.

### A22 — P2: boot B реализован swap A/B

`selected_b = !select_reg[2] ^ boot_b` меняет также смысл всех последующих обращений A/B, а не только выбор источника boot. Это проектное решение не было согласовано. Нужно выбрать: boot с настоящего B либо отображение выбранного раздела как системного A; интерфейс пользователя должен точно описывать результат.

### A23 — P2: геометрия содержит скрытое отличие от штатного floppy.c

Генератор использует BPB sectors/track. Классический floppy.c выбирает фиксированные 9 либо 18 по размеру >737280, хотя принимает sector<=18. Для обычных 720K/1.44M это совпадает; необычная BPB geometry может расходиться. Нужно ограничить первый профиль реально поддержанными геометриями либо доказать произвольную геометрию штатного BIOS. 12 МиБ не включать в профиль i8272.

## Загрузка, ROM и образ SD

### A24 — P1: проверки boot split между несовпадающими моделями

Firmware проверяет header/payload CRC, RTL commit проверяет geometry и MBR bounds, C-model commit проверяет CRC, но не полную RTL geometry. C-model также мгновенно очищает RAM при commit вместо реальной held/reset sequencer. Прошедший C-test не доказывает RTL commit/handoff. Нужна одна спецификация и интеграционный тест actual HDL CPU + SRAM + SPI SD model + real firmware + classic BIOS.

### A25 — P1: нет boot-time таймаутов/диагностики

`file_wait`/`mem_wait` бесконечно ждут, если peripheral не готов и не устанавливает error. FAIL=EE не различает init, MBR, FAT, missing file, length, header CRC, payload CRC, SRAM или lock. Нет полезной диагностики пользователю. Нужны ограниченное ожидание и stage/error code через индикатор/UART, не сложный новый интерфейс.

### A26 — P2: генератор кладёт несколько источников ROM, но loader использует один

BIOS.BIN, FONT.BIN, ROM0–4.BIN и P601.ROM присутствуют одновременно. Загрузка читает только P601.ROM. Замена отдельного BIOS.BIN ничего не изменит — нужно пересобрать bundle+CRC. То же относится к JSON P601.CFG: он не читается loader; boot/geometry берутся из bundle. Нужно оставить один явный контракт и исключить вводящие в заблуждение дубли либо обеспечить реальную их загрузку.

### A27 — P2: bank set выбран без сравнения с желаемой классической комплектацией

`rom_files` жёстко берёт RAMROMDiskPipnet/rom0–4 вместо стандартного native/Rom. Меньшие ROM зеркалируются в 64 КиБ, что имеет разумное соответствие физическим EPROM, но конкретная конфигурация ROM должна быть названа и сверена. «Классический» ещё не определяет набор Pascal/Basic/UniDOS/Menu.

### A28 — P2: образ по умолчанию не загружает систему

CLI/Makefile без disk-a/disk-b создают чистые FAT12 DATA volumes без кода classic boot. Поэтому такой образ может пройти ROM loader и всё равно не запустить ОС. Для end-to-end проверки нужен штатный system.imz/совместимый boot image в разделе A либо B. Тест одного FAT12 layout не является boot test.

### A29 — P2: 12 МиБ проверены только структурно

Python test проверяет FAT12 BPB/FAT capacity для 12 МиБ, а CHS test — арифметику bounds. Ни ОС на таком диске, ни LBA BIOS, ни чтение/запись через другой controller в этом аудите не запускались. 12 МиБ — согласованный будущий профиль проекта, не универсальный предел FAT12.

### A30 — P2: FAT16-only профиль допустим, но не следует называть FAT12/FAT16 готовым

Раздел 1 формируется и читается только FAT16, MBR type 06/0E. FAT12 loader для первого раздела отсутствует. Пользователь разрешил выбор FAT12 или FAT16, поэтому FAT16 как первый профиль подходит, но нужно явно указать его. Существующий FAT streamer имеет bounds/fragmentation checks; он всё равно подлежит замене программной реализацией.

## Видео, клавиатура и периферия

### A31 — P1: графический stride ограничен неправильно

`classic_video` clamp stride=42 применяется и к graphics, тогда как эталон mc6845.c допускает graphics rHor до48. При rHor43–48 следующие строки читаются с неправильного адреса. Нужно раздельно определять visible columns и memory stride; невидимые столбцы всё равно влияют на шаг строк.

### A32 — P1/P2: видеoadреса не ограничены base RAM

DMA-вычисления имеют 21-bit результат. При start близком к FFFF или при graphics shift×8 перенос может уйти в физические ROM banks вместо wrap 16-bit base address. Эмулятор явно приводит адрес к word и имеет правила wrap; RTL эти правила не воспроизводит. Проверить текст/графику у границ и исключить доступ видео к физическим ROM slots.

### A33 — P2: частичное MC6845/PAL поведение

Видеотайминги фиксированы, многие MC6845 regs не участвуют; нужно честно определить совместимый register facade для классических режимов. Cursor address/blink/max raster/центровка/wrap отличаются или не сверены с эталоном. Внутренний cache не инициализируется, нет underrun/error индикации. Горизонтальная/вертикальная развёртка 8MHz×1250 half-lines по замыслу даёт 40ms frame и 20ms field, но нет теста whole-frame, interlace, sync pulses и image comparison.

Font хранится в SRAM и дублируется в writable BRAM, что само по себе не нарушает «font в RAM». Нужно доказать согласованность загрузки и preservation на warm reset. При асинхронном font read синтез может выбрать дорогую mux/lut реализацию: ресурсный результат неизвестен.

### A34 — P1: теряется непрочитанная клавиша

`classic_keyboard` немедленно снимает key_ready при break; `consumed` выставляется, но не используется для удержания/очереди. В эталоне key release откладывается до потребления, есть queue. `tb_unread_key.v` подтверждает make+break без CPU read -> FF. Также новая make перезаписывает старую непрочитанную клавишу.

### A35 — P1: нет отдельного IRQ на клавиатурное событие

Top IRQ формируется только tick_pending от видео. Эмулятор `KBDPresentKey` сразу запрашивает IRQ, а также выполняет 50Hz IRQ. Быстрый tap до следующего field может потеряться полностью из-за A34. Нужны клавиатурный pending и ясная ack-семантика общего IRQ.

### A36 — P2: статус trigger/сложные PS/2 sequences не соответствуют эталону

На make RTL ставит trigger=0, C-эталон — FF. Проверенный keyboard test ожидает статус ПОСЛЕ импульса rs, а CPU в top захватывает значение ДО обновления trigger, поэтому тест не проверяет реально возвращаемый первый status byte. Pause/E1 sequence не разбирается целиком; промежуточный 14 трактуется как Ctrl. Caps/Alt подавляются; LED-команды клавиатуре отсутствуют. Нужны CPU-visible status tests и полный выбранный минимум set2 state machine.

### A37 — P2: недостающая мелкая классическая семантика

MC6845 address register хранит только low4 вместо полного последнего записанного byte (эталон сохраняет iomap[0]); E629 compatibility shadow в E62D отсутствует; page selector/прочие writes не воспроизводят базовые RAM shadows, которые оставляет эмулятор. Что из этого настоящее железо, а что эмуляторная совместимость, нужно отделить; для штатных ROM тестировать наблюдаемое поведение.

Tick IRQ level и read-clear E62B есть, но entry/ack/RTI ещё не сопоставлены с BIOS. UART TX принудительно idle; audio просто дублирует speaker — приемлемая основа, но не тестировались. На сегментных портах 1FF выставляет DIG=1, а документация выключения требует DIG=0/катоды1; это исправить при board-top review.

## Сборка, ресурсы, происхождение и тесты

### A38 — P0/P1: отсутствует полный flow сборки и ограничений платы

Нет LDF/LPF для нового проекта, target device/pin/timing profile не зафиксирован в README. hardware-lcd требует именно SRAM pinout; старые проекты имеют разные grade/package/temperature target. Q1=12МГц предполагается, actual marking неизвестна. Не проверены clock route, reset release, I/O constraints, память EBR/LUT budget и частота критических combinational путей (font mux, 32-bit multiplication/geometry checks).

Старую прошивку/LPF нельзя просто объявить готовым профилем. Обязательны новый project manifest, все pin assignments и post-fit/timing reports.

### A39 — P1: Makefile не соответствует объёму заявленных тестов

`make test` запускает 4 Python cases и только tb_memory, без firmware execution, SD pin model, FDC, keyboard, FAT, boot ports или top integration. Генерация fixture не зависит от loader.asm/native inputs, что позволяет использовать устаревший LOADER.BIN в старом image. В аудите это уже проявилось: после смены I/O адресов старый image давал EE; после пересоздания image тест прошёл.

Нужны воспроизводимые dependencies/fixtures и один test command с прозрачным покрытием. CLI отказ перезаписи output полезен для реальных образов, но тестовые fixtures должны пересоздаваться контролируемо.

### A40 — P2: vendor provenance и лицензирование не оформлены

cpu68 содержит указание GNU public license без версии; исходник сохранён, но нет отдельного provenance с URL, точной ревизией/SHA и описанием местных изменений. Keyboard tables производны от эмулятора и также требуют сохранения происхождения. Это не повод менять лицензии наугад; нужно документировать имеющиеся notices и источник.

## Пересмотренная схема реализации

1. Разделить `board_top_hardware_lcd`, classic core, CPU-bus adapter, SRAM arbiter и reset supervisor. Все запросы имеют accept/inflight/done, latched address/type/owner. У каждого reset описаны сохраняемые и сбрасываемые state.
2. Сохранить классическое окно I/O E600–E6FF и штатные устройства. SPI нового HD6303 ABI разместить в E660–E664: идентичная семантика с изменённой базой. Остальные загрузочные регистры пересмотреть и зафиксировать в едином include/спецификации; разросшийся файловый MMIO удалить.
3. Первичный BIOS в небольшой FPGA ROM исполняется на MC6800 при cold boot. Он через SPI программно инициализирует SD, читает MBR/FAT16, находит LOADER.BIN первого раздела и загружает его в RAM. Штатный BIOS при этом ещё не виден на reset vector.
4. RAM loader через те же BIOS SPI/sector services загружает и проверяет BIOS/font/ROM banks, инициализирует RAM disk при cold boot и готовит partition map. Для физических ROM slots оставить только необходимое boot-only окно/порты записи; lock применяется ко всем writers.
5. Завершение загрузки имеет явный, проверенный handoff. После успешной полной инициализации устанавливается retained `rom_valid/locked`; boot overlay исчезает безопасно, CPU начинает classic BIOS. Кнопка reset затем направляет CPU непосредственно в загруженный BIOS, сохраняя ROM/font/lock/RAM disk. Ошибка/незавершённая cold load не может выставить valid.
6. На первом этапе i8272 остаётся CPU-visible controller. Его SD backend переводит CHS в LBA строго внутри A/B partition bounds; это внутренний способ хранения floppy, а не новый CPU-visible LBA controller. SPI ownership и SD addressing state между CPU boot и backend определяются явно. Прямой SPI и backend не могут одновременно менять SD state.
7. Полная i8272 модель сверх потребностей BIOS может быть отложена, но поддержку именно штатного BIOS подтвердить трассами READ/WRITE/FORMAT/seek/sense/TC/reset и end-to-end system boot. Boot B не должен незаметно менять A/B после загрузки.
8. Затем отдельным профилем добавить CPU-visible LBA controller и адаптацию BIOS/driver для A/B до согласованных 12 МиБ. Не смешивать этот профиль с первой классической версией.
9. Видео: воспроизвести classic memory addressing, stride/cursor/font semantics, затем тестировать изображение и PAL целым frame; PS/2: unread queue/consumption и IRQ. Проверить единый SRAM arbiter под video load.

Размещение SRAM можно сохранить: base RAM 00000–0FFFF; пять ROM banks 10000–5FFFF; BIOS 60000–60FFF; font 61000–617FF; RAM disk 80000–FFFFF. Оно занимает менее 2 МиБ. A/B остаются на SD и не обязаны целиком помещаться в SRAM.

## Очередность исправления и критерии выхода

1. Полный комплект исходников + project flow; исправить parse/VHDL units. Базовая сборка должна быть воспроизводимой.
2. CPU ISA и bus adapter/arbiter/reset tests, включая два воспроизведённых класса гонок. CPU boot исполняется настоящим HDL ядром.
3. Программный SD/FAT16 boot на MC6800; убрать аппаратный файловый слой. SPI register-level contract tests против нового эмулятора.
4. ROM loader/lock/handoff: исполнить реальные инструкции BIOS после cold boot, повторить warm reset без SD-ROM reads и проверить ROM/RAM disk contents. Reset во время каждого вида SRAM/SD операции.
5. End-to-end floppy system boot, last-sector read/write, format, drive switch, invalid geometry, SD failure/recovery. Затем video/keyboard integration.
6. Diamond fit/STA с hardware-lcd pinout; только после этого аппаратные испытания. Нельзя считать проход C-модели или изолированного RTL testbench заменой этих критериев.
